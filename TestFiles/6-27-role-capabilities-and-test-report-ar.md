# دراسة الأدوار والصلاحيات ونتيجة الاختبارات الحالية

تاريخ التدقيق: 2026-06-27

## الخلاصة التنفيذية

- مصدر الحقيقة المستخدم: `UserSystemRole`، جميع Controllers، خصائص `Authorize`، الخدمات التي تطبق نطاق الوصول، وSignalR Hubs.
- عدد الأدوار الفعلية: 7.
- عدد HTTP endpoints الحالية: 164 endpoint موزعة على 17 Controller.
- المسارات العامة التي لا تحتاج تسجيل دخول: 26 endpoint.
- المسارات المشتركة التي تحتاج أي مستخدم مسجل: 16 endpoint.
- المسارات المقيدة بأدوار محددة: 122 endpoints.
- SignalR: عدد 2 Hubs؛ `ChatHub` فيه 5 methods قابلة للاستدعاء، و`NotificationHub` قناة استقبال فقط.

عدد الـendpoints التي يستطيع كل role الوصول إليها يشمل المسارات العامة والمشتركة:

| Role | عدد endpoints المتاحة |
|---|---:|
| SuperAdmin | 85 |
| Secretary | 97 |
| Doctor | 68 |
| Patient | 65 |
| AuthorizedMember | 53 |
| LaboratoryTechnologist | 52 |
| RadiologyTechnologist | 45 |

> العدد الأعلى لا يعني صلاحية أعلى دائمًا؛ مثلًا السكرتير يملك مسارات كثيرة مكررة لإدارة أنواع الموظفين داخل عيادته، بينما SuperAdmin يملك مسارات أوسع نطاقًا.

## القدرات العامة قبل تسجيل الدخول

هذه ليست مرتبطة بـrole، ويمكن لأي شخص استدعاؤها حسب الكود الحالي:

- تسجيل الدخول: `POST /api/Auth/login`.
- إنشاء حساب Patient وDoctor وAuthorizedMember وLaboratoryTechnologist وRadiologyTechnologist.
- لا يوجد تسجيل عام لـSecretary؛ إنشاؤه يتطلب SuperAdmin.
- لا يوجد endpoint لإنشاء SuperAdmin.
- نسيان كلمة المرور، إعادة تعيينها، التحقق من البريد، وإعادة إرسال رمز التحقق.
- عرض قائمة العيادات: `GET /api/Clinics`.
- جميع 15 مسارًا داخل `StandardsController` عامة حاليًا: بحث LOINC وICD-10 وRadiology Playbook وأنواع الصور والبحث الموحد وRxNorm.

## القدرات المشتركة لكل مستخدم مسجل

كل الأدوار السبعة تملك ما يلي بالإضافة إلى صلاحيات role الخاصة بها:

### Chat

- فتح محادثة مع أي User موجود في النظام؛ لا يوجد تقييد حالي حسب الدور أو العيادة أو وجود علاقة علاجية.
- عرض المحادثات والرسائل مع paging.
- إرسال Text أو Image أو Audio.
- تعليم الرسائل كمقروءة.
- تنزيل ملفات المحادثة من route محمي وبعد فحص عضوية المحادثة.
- عبر `ChatHub`: `JoinChat` و`LeaveChat` و`SendTextMessage` و`MarkAsRead` و`SetTyping`.

### Notifications

- عرض إشعارات المستخدم نفسه مع فلاتر `all/read/unread` وpaging.
- تغيير حالة إشعار يخص المستخدم نفسه.
- تعليم كل إشعاراته كمقروءة.
- استقبال الإشعارات الحية عبر `NotificationHub`.

### Reminders

- عرض وتفصيل وتعديل وإخفاء reminders التي يكون المستخدم مشاركًا فيها.
- إنشاء reminder فقط إذا كان المستخدم هو الـPatient أوDoctor أوAuthorizedMember المذكور في الطلب، مع التحقق من ارتباط AuthorizedMember بالمريض.
- عرض وتعديل إعدادات التذكير الشخصية.
- عمليًا SuperAdmin وSecretary وفنيو المختبر/الأشعة يمرون من بوابة `[Authorize]`، لكنهم لا يستطيعون إنشاء reminder سريري صحيح لأن النموذج يطلب Doctor وPatient ومشاركًا مطابقًا.

## 1. SuperAdmin

يستطيع:

- إنشاء حساب Secretary.
- إنشاء وتعديل وتعطيل وتفعيل العيادات.
- تعديل أو تعطيل وتفعيل حساب Secretary من خلال مسارات العيادة.
- عرض جميع السكرتارية، عرض غير المرتبطين بعيادة، عرض سكرتارية عيادة، إسناد سكرتير لعيادة أو إزالته منها.
- عرض وتصفية وجلب وتعديل وتعطيل وتفعيل Doctor وPatient وLaboratoryTechnologist وRadiologyTechnologist على مستوى النظام.
- عرض كل المواعيد أو مواعيد عيادة محددة، وجلب موعد مفرد.
- إنشاء وتعديل وتعطيل وتفعيل أي موعد، مع بقاء قواعد صحة الطبيب/المريض والتعارض الزمني مطبقة.
- استخدام كل القدرات العامة والمشتركة المذكورة أعلاه.

لا يملك حاليًا:

- صفحة `me` أو endpoint لتعديل ملفه الشخصي مباشرة.
- endpoints الطبيب السريرية أو بوابة المريض/المفوّض أو معالجة نتائج المختبر.

## 2. Secretary

يستطيع، ضمن العيادة المرتبط بها:

- عرض dashboard يحتوي أعداد الطلبات المعلقة، تسجيلات المرضى، التقارير، slots ومواعيد اليوم وأحدث التسجيلات.
- تعديل بيانات عيادته عبر `PUT /api/Clinics/my-clinic`.
- عرض سكرتارية عيادته، وإسناد/إزالة سكرتارية وفق قيود الخدمة، وتعديل/تعطيل/تفعيل حساب Secretary من مسارات العيادة.
- عرض وتعديل وتعطيل وتفعيل مرضى وأطباء وفنيي مختبر وفنيي أشعة عيادته.
- استخدام المسارات العامة لإدارة هذه الملفات مع منع الوصول إلى عيادة أخرى على مستوى الخدمة.
- عرض مواعيد عيادته وجلب موعد مفرد، وإنشاء وتعديل وتعطيل وتفعيل موعد داخل عيادته.
- استخدام Chat وNotifications وReminders والـStandards.

لا يملك حاليًا:

- endpoint لإنشاء حساب Doctor أوPatient أوفني؛ التسجيل لهذه الأدوار عام حاليًا، وتسجيل Secretary للـSuperAdmin فقط.
- endpoints لمراجعة وقبول/رفض طلبات تنزيل السجلات، رغم أن dashboard يحسب عددها.
- endpoints فعلية لإنشاء التقارير رغم وجود جداول `Reports` و`ReportInformations` وعداد في dashboard.

## 3. Doctor

يستطيع:

- عرض وتعديل ملفه الشخصي وتغيير كلمة مروره.
- عرض dashboard: مواعيد اليوم، الطلبات المخبرية/الشعاعية المعلقة، الرسائل غير المقروءة، المواعيد القادمة، وتوزيع الأسبوع.
- عرض جدوله بتجميع يومي وعرض تفاصيل موعد يخصه.
- قراءة قائمة مواعيده أو موعد يخصه عبر `AppointmentsController`.
- لا يستطيع إنشاء أو تعديل أو تعطيل أو تفعيل المواعيد من `AppointmentsController` حسب الصلاحيات الحالية.
- عرض السجلات الطبية والبحث/filter/paging، عرض التفاصيل، وتنزيل الملف.
- رفع سجل طبي لموعد: Visit أوLab Result أوImaging Result، مع عرض categories المبنية على standards وسجل الرفعات والتفاصيل والتنزيل.
- إنشاء طلب فحص مخبري لمريض واختيار LOINC وعيادة الفحص والأولوية، ثم عرض طلباته وتنزيل النتيجة.
- إنشاء طلب تصوير لمريض واختيار imaging standard وعيادة الأشعة والأولوية، ثم عرض طلباته وتنزيل النتيجة.
- استخدام Chat وNotifications وReminders والـStandards.

ملاحظة نطاق مهمة: استعلام السجلات الطبية للطبيب لا يفلتر حاليًا حسب الطبيب أو عيادته أو علاقة علاجية. الاختبار الموجود يثبت أن الطبيب يستطيع قراءة سجل من عيادة أخرى. كذلك إنشاء طلب Lab/Imaging يتحقق من وجود المريض والعيادة لكنه لا يفرض أن المريض تابع للطبيب أو لنفس العيادة.

## 4. Patient

يستطيع:

- عرض وتعديل ملفه الشخصي فقط، وجلب ملفه بواسطة id الخاص به.
- عرض dashboard: المواعيد القادمة، الرسائل والإشعارات غير المقروءة، ملخص السجلات، والزيارات حسب العيادة.
- عرض مواعيده وجلب موعد يخصه.
- إنشاء وتعديل وتعطيل وتفعيل موعد لنفسه، بشرط أن يكون الطبيب والمريض في العيادة نفسها وعدم وجود تعارض زمني.
- عرض سجلاته الطبية فقط مع filter/search/paging وعرض التفاصيل.
- تنزيل السجل غير المصنف High severity؛ السجل High يُمنع من التنزيل المباشر.
- إنشاء طلب تنزيل وعرض سجل طلباته وحالاتها.
- عرض Authorized Members المرتبطين به، دعوتهم بالبريد، عرض/إلغاء الدعوات المعلقة، وإزالة التفويض.
- استخدام Chat وNotifications وReminders والـStandards.

لا يملك حاليًا:

- endpoint لإنشاء طلب Lab أوImaging مباشرة؛ الطبيب هو الذي ينشئه.
- مسارًا فعالًا يكمل تنزيل High-severity record؛ لا توجد مراجعة للطلب في Controllers الحالية.

## 5. AuthorizedMember

يستطيع:

- عرض dashboard وملفه الشخصي للقراءة فقط.
- عرض المرضى المرتبطين به وتفاصيل كل مريض.
- عرض مواعيد المرضى المرتبطين به مع فلاتر التاريخ و`upcomingOnly`.
- عرض السجلات الطبية للمرضى المرتبطين به مع filter/search/paging والتفاصيل.
- تنزيل السجلات غير High severity.
- عرض الدعوات المرسلة إليه وقبولها أو رفضها؛ القبول ينشئ علاقة التفويض.
- استخدام Chat وNotifications وReminders والـStandards.

لا يملك حاليًا:

- تعديل ملفه الشخصي.
- حجز أو تعديل موعد للمريض المرتبط.
- إنشاء طلب تنزيل High-severity record نيابة عن المريض أو إتمام دورة الموافقة.

## 6. LaboratoryTechnologist

يستطيع:

- عرض وتعديل ملفه الشخصي وجلبه بواسطة id الخاص به.
- عرض Lab templates وتفاصيل template.
- عرض work items المسندة إليه، إضافة إلى الطلبات غير المسندة داخل عيادته.
- إنشاء نتيجة مخبرية structured result وفق template والتحقق من القيم والـaccession number والعينة والأوقات.
- عرض نتيجة يستطيع الوصول إليها.
- توليد PDF للنتيجة، حفظه في السيرفر، وتنزيله من route محمي.
- استخدام Chat وNotifications وReminders والـStandards.

لا يملك حاليًا:

- إنشاء طلب فحص؛ الطلب ينشئه Doctor.
- الوصول لطلب مسند لفني آخر أو لعيادة أخرى.

## 7. RadiologyTechnologist

يستطيع حاليًا:

- عرض وتعديل ملفه الشخصي وجلبه بواسطة id الخاص به.
- استخدام Chat وNotifications وReminders والـStandards.

لا يملك حاليًا:

- Controller أو endpoints لقائمة Imaging work items.
- رفع/تسجيل نتيجة تصوير أو إكمال Imaging request.
- عرض request مسند إليه رغم أن خدمة الطبيب قد تضع `RadiologyTechnologistId` عند إنشاء الطلب.

هذه فجوة وظيفية واضحة: role موجود ويمكن تسجيله وإدارته، لكن workflow الأشعة من جهة الفني غير منفذ.

## نتائج الاختبار المنفذة

### الاختبارات الموجودة قبل التدقيق

- النتيجة: 102 Passed، صفر Failed، صفر Skipped.
- تغطي Chat/SignalR/file security، Doctor portal، AuthorizedMember، Lab results/PDF، Standards، Lab/Imaging request creation، Doctor uploads، Notifications، Reminders، وبعض appointment filtering.

### اختبارات الصلاحيات المضافة في هذا التدقيق

الملف: `HSCSAPI.Tests/RoleAuthorizationSurfaceTests.cs`.

- النتيجة: 6 Passed، صفر Failed، صفر Skipped.

يتحقق من:

- وجود تصنيف معروف لكل واحد من الـ164 actions وعدم وجود endpoint غير مدروس.
- تطابق كل action مع Public أوAuthenticated أوقائمة roles المحددة.
- تجربة قرار السماح/المنع لكل role على كل action؛ أي 7 × 164 = 1148 مقارنة صلاحية.
- أن كل role مكتوب في `[Authorize(Roles=...)]` موجود فعلًا في `UserSystemRole`.
- عدم وجود route متكرر لنفس HTTP verb والمسار.
- حماية `ChatHub` و`NotificationHub` ووجود methods الـChat المتوقعة فقط.
- تثبيت عدد المسارات المتاحة لكل role كما في جدول التقرير.

### التشغيل النهائي للحزمة كاملة

- الأمر: `dotnet test .\HSCSAPI.Tests\HSCSAPI.Tests.csproj --no-restore --collect:"XPlat Code Coverage"`.
- النتيجة النهائية: **112 Passed، صفر Failed، صفر Skipped**.
- ظهر تحذير package واحد `NU1510` لأن `Microsoft.AspNetCore.SignalR.Common` قد يكون غير ضروري؛ لم يمنع build أو tests.

### حدود الإثبات

- الاختبارات الحالية Component/Service tests وتعتمد غالبًا على EF Core InMemory، وليست رحلة HTTP end-to-end ضد SQL Server حقيقي.
- تم التحقق من عقد authorization والroutes لكل 164 endpoint، لكن ليس صحيحًا الادعاء أن body النجاح والفشل لكل endpoint نُفذ عبر HTTP فعليًا.
- إرسال البريد الحقيقي وRxNav الحقيقي وملفات البيئة الإنتاجية لم تُختبر live في هذا التشغيل. تم تطبيق Migration التفعيل بنجاح على قاعدة البيانات المعرّفة حاليًا، لكن لم يُختبر إنشاء قاعدة SQL Server جديدة من الصفر.
- لذلك النتيجة الدقيقة: البناء والاختبارات الآلية الحالية ناجحة، وسطح الصلاحيات كامل التغطية عقديًا، لكن توجد فجوات وظيفية/أمنية معروفة أدناه ولا يجوز القول إن كل workflow مكتمل.

## الملاحظات الحرجة التي ظهرت من الدراسة

1. **Doctor medical records scope:** الطبيب يستطيع حاليًا قراءة سجلات من عيادات أخرى؛ لا يوجد فلتر علاقة علاجية/طبيب/عيادة في query.
2. **Public professional registration:** إنشاء Doctor وLaboratoryTechnologist وRadiologyTechnologist متاح دون authentication؛ يكفي ClinicId صحيح وبيانات license غير مكررة.
3. **High-severity download workflow غير مكتمل:** المريض ينشئ طلبًا، لكن لا يوجد endpoint للسكرتير لمراجعته، ومسار التنزيل يمنع High دائمًا ولا يفحص طلبًا Approved.
4. **RadiologyTechnologist workflow غير منفذ:** لا توجد قائمة عمل أو إدخال/رفع نتيجة.
5. **Chat واسع جدًا:** أي مستخدم مسجل يستطيع فتح chat مع أي User آخر دون قيد role/clinic/relationship.
6. **Standards أصبحت Public في نسخة العمل الحالية:** `StandardsController` لا يحمل `[Authorize]` حاليًا. يجب تثبيت هل هذا مقصود قبل الإنتاج.
7. **Doctor appointment permissions:** الطبيب يقرأ مواعيده لكنه لا يستطيع إنشاءها أو تعديلها أو تعطيلها أو تفعيلها؛ هذا هو السلوك الحالي وقد يكون قرارًا أو نقصًا حسب المطلوب التجاري.
